## Semantic decisions and limits

1. **Definition reuse:** one part/action/requirement/verification definition can be referenced by typed usages in a root composition or software role. Do not create duplicate definition notes.
2. **No custom relationships:** generic `dependency` is not an exact equivalent of use-case realization or stakeholder motivation. It captures only dependence; precise trace semantics remain an open decision.
3. **Allocation is not satisfaction:** candidate responsibilities are modeled without claiming implemented software meets the requirements.
4. **Rule provenance is metadata and evidence:** rule-reference `Info` notes are deliberately *not* treated as SysML model elements or invented dependency targets.
5. **Only documented behavior ownership was decomposed:** knowledge discovery, relationship traversal, projections, editing and import reconciliation are separated; Core, Base Vault and Bootstrap need distinct additional function definitions for full coverage.
6. **Runtime caveat:** the Workbench scanner recognizes `dependency` and `perform` syntactic forms inside definitions, but its ability to resolve all external qualified names, index all new relationship types, and display/round-trip these links is **not verified**. Native parser acceptance is also outstanding.
7. **Original governance remains unchanged:** no edits made to `MDSE_v2` governing documents or 386 rule reference notes.
